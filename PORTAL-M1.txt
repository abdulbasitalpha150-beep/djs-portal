1. Project Overview
-------------------
The project is a web-based Transportation Management System (TMS) client portal for a freight brokerage environment. It is designed to support a brokerage operating across lead generation, customer onboarding, quote approval, carrier management, load execution, invoicing, commissions, notifications, and admin oversight.

The portal appears to be a full-featured internal operations platform rather than a single-purpose CRM. The codebase supports both CRM-style workflows (leads, customers, follow-ups) and TMS-style operations (loads, invoices, carrier records, commissions).

Primary business problem solved
- Organize and track freight-related opportunities and operations from intake to settlement.
- Provide role-based visibility so agents, team managers, operations personnel, accounting, and administrators can work within the same system without exposing irrelevant data.
- Enforce approval workflows for sensitive actions such as creating or changing records.
- Maintain auditability with activity logging and notification records.

Primary users
- Internal agents and sales representatives
- Team managers and lead agents
- Operations managers and administrators
- Accounting personnel
- Client-facing or internal stakeholders reviewing status and approvals

Architecture summary
- Frontend: React with TanStack Router and TanStack Start.
- Backend/API layer: custom request router in the server entry, handling API routes directly from the application server.
- Database: MongoDB via Mongoose models.
- Authentication: JWT access/refresh cookies plus server-side session validation.
- UI pattern: component-based React UI with shadcn-style primitives and Tailwind.
- State/data access: React Query is configured for routing context, and API calls are made directly through a custom apiFetch helper.

Hosting assumptions
- The app is structured for a Node.js/Vercel-style deployment with Nitro/Vite Start configuration.
- The server expects environment variables for MongoDB and JWT secrets.
- The frontend and API are served through the same application entrypoint and route handling system.

3. User Roles
--------------
The role system is defined in src/lib/roles.ts. Roles include:
- owner
- admin
- ops_manager
- team_manager
- leadagent
- agent
- trainee
- accounting
- suspended

Role summaries
- owner: full access; can manage everything including users, teams, and admin operations.
- admin: full access similar to owner with admin-specific controls.
- ops_manager: broad operational access, approvals, dashboard, reports, notifications, bookings, and activity.
- team_manager: scoped visibility to their team; can access team-level records and approvals.
- leadagent: similar to team managers for operational workflows, with team-centric visibility.
- agent: can work with leads, customers, quotes, carriers, loads, documents, commissions, activity, notifications, and follow-ups, but has more restricted approval abilities and record ownership scope.
- trainee: read-heavy and limited; can view many domains but is more restricted than agents in write actions.
- accounting: focused on commissions, invoices, reports, notifications, documents, and dashboards.
- suspended: no meaningful access; UI displays a suspended account screen.

Role capability matrix
- The app uses a capability matrix rather than hard-coded route checks alone.
- Capabilities include dashboard, leads, customers, quotes, carriers, loads, documents, onboarding, commissions, invoices, activity, approvals, reports, notifications, users, teams, audit, admin, booking_actions, approval_actions, commission_rules, and followups.
- The navigation shell filters menu items based on this capability matrix.

5. End-to-End Workflow
----------------------
Current implementation flow, as reflected by the codebase:

1. Login
   - User submits email and password to /api/auth/login.
   - Server validates the credentials, checks that the account is active, and sets auth cookies.
   - The client stores a session in the auth context and restores it on refresh.

2. Dashboard
   - The dashboard loads from /api/dashboard.
   - The API calculates role-based metrics from MongoDB collections such as leads, quotes, loads, customers, carriers, invoices, commissions, notifications, approvals, follow-ups, and onboarding documents.
   - Different roles receive different KPI sets and widgets.

3. Lead and customer management
   - Agents or managers create leads and customers.
   - Leads can be edited, reassigned, and tracked through a pipeline stage history.
   - Lower-privilege users may create leads through an approval request rather than a direct persistence action.

4. Quotes and approvals
   - Quotes are modeled by QuoteRequest and support approval status.
   - Lower-level users create records that require approval; approvers can approve, reject, or request changes.
   - Approval outcomes produce notifications and can persist the underlying record if approved.

5. Carriers and loads
   - Carriers can be created and progressed through vetting statuses.
   - Loads represent freight transactions and include pickup/delivery data, financial information, shipment details, documents, and statuses.
   - Loads are central to the TMS workflow and are used in dashboards, commissions, invoicing, and reporting.

6. Invoices and commissions
   - Invoices are created from billing snapshots and include line items, totals, payments, and status.
   - Commissions are tracked separately from loads and include payout status and month/year.

7. Follow-ups and activity
   - Activity records and follow-ups are used for accountability and task planning.
   - Notifications are emitted for approval outcomes, comments, and system events.

8. Admin operations
   - Administrators can manage users, teams, and system reset/cleanup functions.
   - Audit logs record authentication and other actions.

6. Module Documentation
-----------------------
Leads
- Purpose: track potential freight customers or prospects.
- Key fields include company name, contact info, status, pipeline stage, owner/agent, notes, and pipeline history.
- Business behavior: duplicate company name checks are enforced for new leads.
- Approval behavior: agents and trainees can create leads that enter an approval state first.
- Data relationships: ownerId links to a user, and reassignment history records ownership changes.

Customers
- Purpose: represent business customers that have been accepted into the system.
- Supported statuses: submitted, review, approved, rejected.
- Credit flow: customer credit status is tracked separately (pending, approved, rejected).
- Used as a key dependency for invoice and load work.

Quotes
- Purpose: represent freight pricing opportunities between customer and carrier.
- Fields include lane, equipment type, commodity, customer rate, carrier cost, margin amount, margin percent, notes, approval status, expiry, and win/loss reason.
- Margin is auto-calculated as customerRate - carrierCost, and margin percent is derived from the margin ratio.
- Approval flow is implemented around quote requests.

Carriers
- Purpose: maintain carrier vendor records and vetting information.
- Carriers have legal name, MC/DOT numbers, contact info, address, equipment types, service areas, insurance details, review history, and vetting checks.
- Review lifecycle includes pending, under_review, approved, rejected, or suspended.

Loads
- Purpose: represent the operational freight shipment lifecycle.
- Fields include quote request linkage, agent, customer, carrier, pickup/delivery details, shipment properties, pricing, margins, invoice/payment status, and document status flags.
- Data is central to dashboards, commissions, invoice generation, and operational tracking.
- Statuses include draft, quoted, booked, dispatched, in_transit, delivered, invoiced, paid, cancelled.

Invoices
- Purpose: bill customers for freight transactions.
- Invoices include billing snapshot values, line items, financial totals, payment history, and status.
- Statuses include draft, sent, partially_paid, paid, overdue, cancelled.

Commissions
- Purpose: calculate and track agent commissions.
- Each commission record links to an agent and load and stores gross margin, tier, percent, amount, payout status, and month/year.

Follow-ups
- Purpose: assign tasks to users for maintaining client relationships.
- Fields include lead/customer linkage, due date, priority, notes, and completion state.

Activity and audit
- Activity logs are used for accountability, tracking events, and notification context.
- Audit events are recorded for login, logout, password changes, and other actions.

Documents and onboarding
- The codebase includes onboarding-related models and routes, though the current navigation has some of these modules commented out in the sidebar.
- Documentation and training requirements appear to be partially wired in.

8. Authentication Flow
----------------------
Authentication is cookie-based and uses JWTs.

Login flow
- POST /api/auth/login accepts email and password.
- The server validates the submitted body using Zod schema validation.
- If the user exists and the password is correct, the server checks that the account is active and not suspended.
- The server updates lastLoginAt, lastAuthAction, and IP address before issuing tokens.
- Two cookies are set: accessToken and refreshToken.

Session restoration
- On app startup, the auth context calls /api/auth/session to restore the active session from the access token cookie.
- If the access token is missing or invalid, the session is cleared.

Refresh flow
- The client sends a request to /api/auth/refresh using the refresh cookie.
- The server validates the refresh token and issues a new access token.

Logout flow
- POST /api/auth/logout clears auth cookies and updates the user’s last logout metadata.
- The frontend also triggers a logout signal on timeout.

Password change flow
- The app introduces a temporary-password state and shows a modal forcing the user to change the password on next login.
- Password change uses /api/auth/change-password and validates current/new/confirm password, minimum length, and monthly change limits.

Authorization model
- Authentication is implemented server-side via requireAuth and requireRole helpers.
- Role-based access is enforced in the API layer and in the frontend navigation using the capability matrix.

9. API Documentation
--------------------
The main app API router is centralized in src/api/index.ts and dispatches to route handlers under src/api.

Authentication endpoints
- POST /api/auth/login
  - Authenticates a user and returns a user session payload.
  - Requires email and password.
  - Returns 401 for invalid credentials and 403 for inactive/suspended accounts.

- POST /api/auth/logout
  - Clears auth cookies and updates logout metadata.

- POST /api/auth/refresh
  - Refreshes the access token from a refresh cookie.

- GET /api/auth/session
  - Returns the current session user if the access token is valid.

- POST /api/auth/change-password
  - Changes the current password and clears temporary-password status.

User management endpoints
- GET/POST/PATCH/DELETE /api/users
  - Manage users and their account details, roles, teams, and status.

Team endpoints
- GET/POST/PATCH/DELETE /api/teams
  - Manage teams and team membership.

Lead endpoints
- GET/POST/PATCH/DELETE /api/leads
  - List, create, update, and delete leads.
  - Includes approval-aware create behavior for lower-privilege roles.

Customer endpoints
- GET/POST/PATCH/DELETE /api/customers
  - Manage customer records.

Quote endpoints
- GET/POST/PATCH /api/quotes
  - Manage quotes and quote records.
- POST /api/quotes/:id/approve
  - Approve a quote request by ID.

Carrier endpoints
- GET/POST/PATCH/DELETE /api/carriers
  - Manage carriers and their vetting state.

Load endpoints
- GET/POST/PATCH/DELETE /api/loads
  - Manage loads and their operational and financial state.

Activity endpoints
- POST /api/activity/log
  - Logs an activity event.

  - Track attendance or work state.

Approval endpoints
- GET /api/approvals
  - List approval requests based on role scope.
- POST /api/approvals
  - Create an approval request.
- PATCH /api/approvals
  - Approve, reject, request changes, add comments, or update a request.

Invoice endpoints
- GET/POST/PATCH/DELETE /api/invoices
  - Manage invoices.

Follow-up endpoints
- GET/POST/PATCH/DELETE /api/followups
  - Manage follow-up tasks.

Dashboard and notifications
- GET /api/dashboard
  - Returns role-based dashboard data.
- GET /api/notifications
  - Retrieve notifications.
- POST /api/notifications
  - Create or update notifications.
- GET /api/notifications/kpi-summary
  - Provide KPI summaries for notifications.

Admin endpoints
- POST /api/admin/reset-system
  - Resets or clears system data.

Audit endpoints
- GET /api/audit-logs
  - View audit logs.

10. Business Logic
------------------
Approval chains
- The application implements a role-aware approval workflow for lower-privilege users.
- Approvers can approve/reject/request changes based on role and team scope.
- Team managers and lead agents are restricted to their own team’s requests.

Status transitions
- Leads support a pipeline stage history.
- Loads support a state progression through shipping lifecycle phases.
- Carriers support review status transitions.
- Invoices and commissions have their own state systems.

Margin and commission logic
- Quote margins are auto-calculated from customer rate and carrier cost.
- Load gross margin values influence dashboard summaries and commission records.
- Commission records track payout status and month/year.

Notifications
- Approval outcomes, comments, and related system events generate notifications.
- Notification payloads include metadata such as module, action, and record ID.

Assignment rules
- Leads and follow-ups can be assigned to specific users or team contexts.
- Reassignment history records changes to ownerId.

23. Application Lifecycle
------------------------
On application start
- The router and app shell mount.
- The auth provider tries to restore a session via /api/auth/session.
- The sidebar and protected routes initialize based on current session and role.

On login
- Credentials are validated and auth cookies are issued.
- Session state is updated in the frontend.
- The user is redirected into the protected app shell.

On navigation
- The protected app shell checks session status and redirects to login if not authenticated.
- Sidebar entries are filtered based on role capabilities.

On CRUD operations
- The frontend calls the REST-style API routes in src/api/index.ts.
- The handler performs validation, persistence, and sometimes approval workflows.
- Local UI state is updated to reflect the server result.

On logout
- Auth cookies are cleared and the auth context resets the client state.
- The user is redirected to the login page.

27. Overall Project Summary
--------------------------
This portal is a role-driven freight brokerage operations platform built on React, TanStack Router/Start, and MongoDB. It combines CRM-style lead and customer management with TMS-style load, invoice, and commission workflows. The system is actively designed around approval chains, role-based visibility, notifications, and analytics.

The most important observation is that the implementation is not merely a static dashboard; it is an operational system with real workflow logic. Leads, approvals, carriers, loads, invoices, commissions, follow-ups, users, and teams are all represented in the code with a meaningful business purpose. The app appears to be a solid internal portal foundation that is already functional for many core workflows, while some features such as the reports page, onboarding/document management, and deeper reporting are only partially surfaced or unfinished.

Suggested future improvements
- Surface the reports feature more prominently and fully implement its route and data views.
- Expand document and onboarding support into full user-facing modules.
- Review and harden the permission model for all write operations.
- Remove or secure sensitive login documentation from the repository.
- Add more comprehensive automated tests and end-to-end coverage for approvals, loads, invoices, and reporting.
